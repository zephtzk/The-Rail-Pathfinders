## Feed operation and secure configuration

`GET /api/notices` reads only TrainServiceAlerts. It shares the adapter cache with `/api/status`; it does not fetch three unrelated crowding feeds for each Phase 4 check. `/api/status` retains the original replay information panel. `/api/bus-arrivals?stop=81111` remains advisory. Unconfigured responses explicitly say `not_configured`; there is no browser secret, client-side provider request, proxy workaround or replacement infrastructure.

Notices: 60-second minimum refresh; crowd reports: 10 minutes. Bus: 30 seconds per supported stop, maximum two concurrent upstream requests and 40 cache entries. Concurrent same-feed callers coalesce. Requests abort after six seconds; payloads have byte bounds. Authentication uses a five-minute backoff; rate limits respect Retry-After; repeated network/malformed failures grow to a ten-minute cap. Notice rate limits are per feed; bus authentication/rate backoff is shared across stops. **All caching/coalescing is per Worker isolate or local process. It is not a distributed cache or globally enforced provider quota.** No new shared infrastructure was provisioned.
