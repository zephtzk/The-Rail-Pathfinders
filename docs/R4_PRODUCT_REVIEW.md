# R4 product review: everyday Singapore commuting

Reviewed 19 September 2026 after the R4 implementation. This is a review of the working local application, retained data, automated user flows and desktop/mobile/large-text screenshots. Google Maps is benchmarked using its current official documentation; this is not a field trial establishing Google’s exact Singapore coverage. Map-failure screenshots intentionally block tiles to verify the fallback and do not measure provider uptime. No production deployment or audience expansion was performed.

## Assessment

R4 is substantially easier to understand, but it is not yet a credible island-wide replacement for Google Maps. Its strongest proposition is a calm companion for a familiar, supported journey: saved personal preferences, clear transfers, deliberate check-ins, optional caregiver coordination, recoverable saved guidance and local spending. The largest obstacle to daily Singapore use is coverage and trustworthy timing, rather than visual polish.

**Exclusive data access is not established by this repository.** LTA describes DataMall APIs as available to registered subscribers with an Account Key. Possessing that key does not show that Google or other developers cannot obtain the same information. Additional organiser-only datasets, licence terms or partnerships would need to be identified before making an exclusivity claim. [LTA DataMall](https://datamall.lta.gov.sg/content/datamall/en.html)

## Functionality and user flow compared with Google Maps

| Commuter task | Established benchmark | R4 assessment |
| --- | --- | --- |
| Find a destination | Google documents address, place-name and map-point routing, alternative routes and departure/arrival time choices. | R4 station/stop search is now readable and precise, but an address saved through Photon is not a routable door-to-door endpoint. Its arrival deadline filters candidates from a chosen departure; it does not calculate the latest departure. This adds planning effort. [Google directions](https://support.google.com/maps/answer/144339?hl=en) |
| Repeat a daily trip | Google supports frequent-trip pinning and alternate departures; real-time versus scheduled information depends on availability. | Saved R4 routes retain preferences and recalculate departure timing. This is useful baseline functionality, not a unique advantage. A home-screen shortcut and easier next-departure switching could improve repeat use without new data, within the supported timetable. [Google transit departures](https://support.google.com/maps/answer/6142130?hl=en) |
| Understand transfers | Clear transit legs, stations, time and transport identity are expected of a mature journey planner. | R4 replaces internal IDs and repeated access/wait rows with a timeline, public line badges and real interchange instructions. Original route indices remain intact. This closes a substantial readability gap; it does not validate previously unknown station paths. |
| Travel with mobility needs | Google documents a wheelchair-accessible transit option. Availability or completeness at every Singapore station is not established by that documentation. | R4 preserves a strict step-free requirement, but cannot start real accessible guidance without verified paths. Honesty is valuable; a disabled capability is not a competitive accessibility advantage. [Google accessible transit](https://support.google.com/maps/answer/6396990?hl=en) |
| Recover from a missed connection | Google documents selecting later transit departures and updating subsequent journey timing. | R4 requires explicit position, civil time and walking spent before checking the remaining route. This is safer than guessing progress, but more demanding. The route changes only after acceptance. Simplifying the position form is a design opportunity; silent boarding/alighting inference is not justified. [Google alternate departures](https://support.google.com/maps/answer/6142130?hl=en) |
| Coordinate with family | Google supports location sharing and arrival/departure notifications, subject to permissions and account/link restrictions. | R4’s possible distinction is explicit transit checkpoints and independent progress/location permissions. Sharing itself is not unique. Current foreground-only collection and unverified external delivery limit confidence when the phone is locked. [Google location notifications](https://support.google.com/maps/answer/11966807?hl=en) |
| Keep guidance during a connection loss | Google explicitly excludes transit, walking and cycling directions from its downloaded offline-map navigation. | R4 can restore an accepted transit plan and its cached instructions, when actual offline readiness is verified. This is a useful bounded difference. It does not provide live information, current closures, downloaded street tiles or new external address search offline. [Google offline limits](https://support.google.com/maps/answer/6291838?hl=en) |
| Understand travel costs | A Singapore commute benefits from familiar fare categories and clear personal expenditure. | R4’s separate spending page is useful: charged amounts replace estimates once; refunds stay with the original trip period. It is a manual/estimated local ledger, not a SimplyGo account or payment integration. No claim is made that Google lacks every comparable fare feature. |

## Design and interaction review

The R4 plan → choose → confirm → start flow now has one authoritative preferences screen and one confirmation action. The clock opens the time picker directly. Station codes, bus termini and the service 23 loop are human-readable. A successful checkpoint returns focus and scroll to current guidance. Station/toilet tools live together; caregiver and spending have their own pages. Week/month spending lists start collapsed. Coverage banners distinguish prototype limits from actual constraints.

Visual review also corrected a long floating trip shortcut that obscured large-text content, mid-word navigation wrapping, a duplicate spending heading, and the need to scroll past the entire timeline to reach Start Journey. These are tested at desktop, 390px mobile and 320px enlarged text. The map fallback remains clearly labelled as schematic.

Remaining improvements **do not require new data**:

1. Give Spending, Settings and Caregiver more usable vertical space by reducing the persistent map area on those pages. Keep the map prominent during planning and travel.
2. Put the next useful action ahead of Finish during early travel. Finish must remain an explicit declaration of arrival, never a timer-triggered action.
3. Use friendlier displayed dates and less second-level precision for assumed walking and bus timing; preserve exact seconds internally and reveal them in timing detail. Precision must not imply measurement.
4. Add a direct saved-commute entry point and simplify the occasional route-recheck form. Retain explicit acceptance, cumulative walking, and permission boundaries.
5. Evaluate multilingual labels, larger touch targets and screen-reader journeys with Singapore commuters, including older people and wheelchair users. Translation and layout work are implementation tasks; actual usability superiority requires research with users.

These are follow-on product recommendations, not unimplemented R4 acceptance requirements or reasons to invent new data.

## Shortfalls blocked by insufficient validated data

“Blocked” below means the capability cannot be honestly delivered from the currently retained evidence. It does not mean the data is impossible to obtain.

| Desired experience | What is missing now | Evidence needed to enable it |
| --- | --- | --- |
| Dependable entrance-to-platform, lift and toilet directions | There are **zero verified real indoor accessible/toilet routes**. The one retained Bugis toilet point lacks checked entrance, floor, hours, gate side and accessibility. The complete graph is fictional training data. | A permitted, maintained, field-checked graph of entrances, gates, platforms, floor transitions and toilet access; stable facility IDs; accessibility attributes; current opening/access conditions. Lift notices must map to graph edges and ambiguous IDs must remain unresolved. [Facility coverage](FACILITY_COVERAGE.md) |
| Reliable end-to-end walk/bus/rail journeys | Only four reviewed exterior connections are enabled, at Paya Lebar and Bugis. Nearby coordinates do not establish road crossings, station entrances or interchange bays. | Connected pedestrian/entrance evidence with permitted crossings, directions, gate boundaries and costs. Basic general routing may be obtainable through another service; verified accessible last-mile routing still needs stronger evidence. [Walking coverage](WALKING_COVERAGE.md) |
| A trustworthy “quieter train” or best departure recommendation | Retained historical crowd samples are expired; no validated per-train or carriage occupancy or reliable supply model drives default route ranking. | Fresh, correctly mapped observations/forecasts with coverage, confidence, expiry and evaluation. Station-level crowd bands cannot establish space on a particular train or guarantee a seat. [Source coverage](DATA_SOURCES.md) |
| Sheltered, comfortable or weather-aware routes | No complete reviewed shelter/indoor pedestrian graph or calibrated user-specific walking times is available. | Maintained shelter, passage, crossing, slope and accessibility attributes linked to usable paths. A weather feed alone cannot establish a dry or accessible route. [Walking limitations](WALKING_COVERAGE.md) |
| Automatic accurate fare totals for arbitrary trips | Only two directional rail OD fare distances are allowlisted. Gate-changing stops and many mixed trips lack reviewed fare evidence. | Official fare distances or a permitted fare-calculation service plus transfer/gate semantics for the actual itinerary. Do not infer fare distance from stop counts or map length. [Fare coverage](FARES.md) |
| Automatic actual spending | The application has no authorised fare-card/SimplyGo transaction connection. | An authorised transaction feed, account consent and reconciliation rules. Manual charges remain available; estimates must not be represented as payments. [Ledger semantics](FARES.md) |
| Precise underground position, automatic boarding or arrival | Browser GPS does not identify a floor, train, platform or successful boarding. | Suitable positioning/operational evidence, confidence handling and device validation. A native app alone would not prove these events. |
| Reliable automatic disruption rerouting | Advisories lack fully validated scope, affected service/segment mappings, effective periods and recovery semantics in the production routing model. | Fresh operational impacts mapped to exact timetable identities, including expiry/conflict handling and demonstrated feasible alternatives. The existing fictional incident workflow is not live evidence. [Rerouting readiness](PHASE4_READINESS.md) |
| Demand-shifting rewards | No programme, eligibility rules, redemption service or evaluated supply/demand response is implemented. | A real authorised incentive programme and reliable measurement, in addition to transport data. The organiser FAQ describes a product aim, not evidence that quieter trips or rewards exist. |

LTA does expose potentially useful arrivals, station crowding and lift-maintenance APIs. The documented crowd feeds are station-level; lift notices do not supply a complete indoor connectivity graph. Such feeds can inform a validated product but cannot replace the missing path, calibration and operational evidence above. [DataMall API guide](https://datamall.lta.gov.sg/content/dam/datamall/datasets/LTA_DataMall_API_User_Guide.pdf)

## Coverage and integration gaps that are not inherently unavailable data

The shipped rail schedule covers 18 September–31 December 2026, with 186 station records, not necessarily 186 unique station complexes. Bus routing supports only services 2, 23 and 28, five complete patterns, ordinary weekdays 09:30–16:30 through 2 October 2026. That excludes peak-hour/weekend bus commuting. R4 did not expand these bounds. [Rail coverage](RAIL_COVERAGE.md), [bus contract](BUS_DATA.md)

Wider bus import, timetable renewal, supported holidays, and putting the existing advisory BusArrival UI into the main experience are integration/validation projects. They should not be described as impossible because Google owns the data. Current bus travel time is distance-based with assumed speed and dwell; a queried stop’s next bus ETA does not validate downstream arrival or a guaranteed interchange. [Bus timing contract](BUS_DATA.md)

Singapore OneMap documents public-transport and pedestrian routing APIs with authentication. It is a plausible candidate for a separately tested address-routing integration; it is not currently connected here, and the published routing interface must not be assumed to provide a verified indoor barrier-free graph. Its documentation was indexed during this review, but direct rendered-page verification returned a JavaScript shell. [OneMap routing documentation](https://www.onemap.gov.sg/apidocs/routing)

Background execution, push delivery, physical-phone accessibility and native integrations need engineering and device testing as well as evidence; they are not all data shortages. Our browser-emulation results do not establish iPhone/Android field reliability.

## Singapore positioning and next investment

Lead with **“your familiar commute, with the guidance and support you choose.”** Local station/stop names, accurate loop descriptions, Singapore civil time, saved walking/accessibility constraints, fare categories and a clear personal ledger are useful local details. The most promising differentiated experience is an independently verified entrance/lift/toilet-aware corridor paired with understandable checkpoints and optional family help. That advantage must come from maintained evidence and execution, not from an unproven claim of exclusive API access.

Prioritise a dependable ordinary-day pilot before a disruption showcase: broaden valid commuting times/services; validate a small complete doorstep-to-destination corridor; expose useful fresh arrivals with honest limits; test repeat journeys with Singapore commuters. Measure planning success, missed-transfer confusion, time to the next useful action, and repeat use. Until that evidence exists, describe R4 as a bounded commute companion with clear coverage rather than a generally better route planner than Google Maps.
